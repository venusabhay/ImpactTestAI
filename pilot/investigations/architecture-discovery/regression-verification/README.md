# Regression Verification — Before Freeze

These four reports were generated by the frozen `analyze_change.py` + `discovery.py` implementation, run against the known repositories, immediately before selecting held-out repositories (per the mandatory ordering: implement → regression-test → **freeze** → select held-out → run → evaluate).

- `social-media-mini-verify-regression.md` — the original `/verify` caching change. The Stage 2B security regression (stale-cache authorization bypass) is reproduced identically: `HIGH` risk, cross-service test fails with the same `SECURITY REGRESSION` assertion, `ESCALATE`. As a genuine, unplanned improvement (not a regression-test requirement, but a natural consequence of broadening validation-target selection to include callers), `post-service` and `user-service` are now also validated and correctly pass.
- `change-a-api-cache-rerun.md` — `user-management-api`'s `protect()` middleware caching change. **Previously: empty impact, empty evidence, `ESCALATE` for the wrong reason (no validation found at all).** Now: `CRITICAL` risk, 4 impacted routes correctly identified via the new middleware-dependency discovery, `REQUIRE_ADDITIONAL_VALIDATION` (once a pre-existing, unrelated environment gap — see note below — is corrected so the real test suite can run at all).
- `change-b-frontend-rerun.md` — the trivial frontend validation change. Unchanged from the original pilot: `LOW` risk, empty impact, `ESCALATE` (no test capability exists for the frontend at all — a real fact about the repository, not a discovery failure).
- `change-c-cross-component-rerun.md` — the `/refresh` contract break. **Previously: empty impact, indistinguishable from Change B.** Now: `MEDIUM` business impact/exposure, the changed route AND the frontend's real dependency on it are both identified with concrete evidence, `REQUIRE_ADDITIONAL_VALIDATION`.

## Note on a pre-existing, unrelated environment gap

Running `npm test` in `user-management-api` (Changes A and C) initially reported `FAILED`, but investigation showed the *exact same* 7 test failures occur on unmodified `main` — traced to a missing `JWT_REFRESH_SECRET` environment variable (the repository has no `.env` file; it's normally supplied via `docker-compose.yml`'s `env_file` outside of a plain `npm test` invocation). This is a pre-existing repository/environment characteristic, unrelated to architecture discovery or to either change under test. It was corrected for these reruns by supplying `JWT_SECRET`/`JWT_REFRESH_SECRET` as environment variables before invoking the analyzer — the same category of legitimate test-environment setup as `--npm-install` for a missing `node_modules`, not a manipulation of results. The reports in this directory reflect the corrected environment; the raw uncorrected output (validation `FAILED` due to the missing secret) is discussed, not hidden, in the main milestone report.
